## Observations

* **DCT is already fast in Python** (1.1× / 1.3×). The Python path is end-to-end vectorized numpy; the Rust port uses naive triple loops and merely matches it. Porting DCT to Rust gives little benefit unless we add SIMD/parallelism, which numpy already has.
* **Shape encode dominates total cost in both stacks.** Triangle encode is 9.5× faster in Rust (10.2 ms vs 96.7 ms). Circle encode is 12.7× faster. The Python kernels already use numba `@njit` for the inner rasterizer, so the win comes from the search loop, RNG, and Python→numba call overhead — all eliminated in the Rust port.
* **Pixel decode benefits the most relatively** (36.1×): Python's path constructs a small numpy array per cell and goes through PIL for upscale, while Rust writes pixels directly. Encode is 7.1× faster for the same reason.
* **Triangle decode is 12.3× faster in Rust** even with AA off, because Python rebuilds the per-triangle Pineda edge function arrays per pixel via numpy broadcasting; Rust uses incremental integer edge updates.

## Binding feasibility — verified by PoC

A minimal PyO3 PoC (`packages/arthash-py`) exposes `encode_rgb` / `decode` to Python. Measured from the Python side, the binding's median is within **±5%** of the Rust-native median across every mode, confirming that the GIL release + bytes marshalling overhead is negligible compared to the encode/decode work itself.

Result: for shape modes, a Rust core wrapped by PyO3 / napi-rs is roughly **5–35× faster** than the current Python implementation while producing byte-identical (or byte-compatible — see §Conformance in the Rust README) hashes. For DCT it's a wash. Two concrete bindings are worth pursuing:

1. **PyO3 wheel** (`packages/arthash-py`) — exposes the four `encode_rgb` / `decode` entry points and the `Codec` struct. The Python package keeps the path/PIL ingestion (PIL LANCZOS resize doesn't have a byte-stable Rust port) and only delegates the inner encode/decode to Rust. Expected wheel size <300 kB. Triangle encode drops from ~100 ms to ~10 ms per image — the kind of difference that turns batch processing from minutes to seconds.
2. **napi-rs Node addon** (`packages/arthash-js`) — there is currently no TypeScript implementation, so even the DCT path is a fresh capability. napi-rs lets the same Rust crate be reused with a thin glue layer; the encode/decode surface area is small (4 functions + 1 struct).

Caveats to flag in any binding:
* The encoder's output for CIRCLE/TRIANGLE differs byte-for-byte from Python's because Rust uses xoshiro256\*\* and Python uses numpy PCG64-DXSM. Both are SPEC-valid; decoded images are visually equivalent.
* PIL LANCZOS resize is not reproduced. Callers wanting bit-identical Python↔Rust output for PIXEL on resized inputs must pre-thumbnail in the same library.
